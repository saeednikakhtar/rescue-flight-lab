# Flight display source and verification

Version 3 adds a smooth airfoil-wing silhouette, detailed hubs/struts and separate surface materials; camera composition leaves more sky and landscape visible. `landscape.js` generates the offline countryside texture and daylight atmosphere. Atmospheric scattering is baked once into the background; aircraft materials alone receive its reflection map, keeping ground and foliage shading inexpensive. Runway numbers and markings are baked into the existing single surface. There is no shadow-map pass or external imagery dependency. The optional frame meter publishes non-visible canvas data attributes for verification; the normal panel has no diagnostics section.

`renderer.js` is the WebGL scene; `airframe.js` builds an illustrative charcoal Orion-inspired unarmed generic UAV visual, with a fuller rounded forward pod, long straight wings, broad upward V-tail, rear pusher and slim gear. The model adds no aircraft-specific dimensions, aerodynamic data, systems or operating behavior. Flight physics remain the native Plane SITL model. Actual pose, AGL, motor output and canopy inflation drive the display. Ground distances are metres, while aircraft and canopy geometry are enlarged twelve times for visibility. Terrain, vegetation, roads and hangars are illustrative and locally flat; the grass strip uses `state.site` and `test-site.json`.

`flight-state.js` is the actual pose/path owner used by both WebGL and the basic canvas fallback. It buffers up to eight timestamped samples and plays them approximately 220 ms behind arrival, with linear position interpolation and quaternion attitude interpolation. The playhead cannot move backwards when packet timing varies. Starting a new session atomically clears buffered poses, canopy, path and camera generation, retires the old session ID and rejects late old snapshots. Same-session mode changes and repositioning stay continuous. Invalid/nonfinite positions, initial near-zero EKF drift far from the site, and implausible jumps are excluded from the path. Until the first usable position arrives, the view holds the known launch reference.

Static aircraft and airfield meshes are batched by material. The canopy fabric is a single vertex-colored mesh; all seams share one line mesh. Tree polygons are reduced and rebuilt only across a large area. The projected aircraft shadow is removed; shadow-map passes remain disabled. The path reuses a bounded GPU buffer, HUD painting is throttled, canvas resizing follows ResizeObserver, and pixel density is capped. The live panel requests revision-2 sparse history deltas when supported and retains compatibility with the older full-state API. Its graph is bounded to 150 seconds / 600 points.

Run `powershell -File graphics-source/build-graphics.ps1` from the package root to rebuild `scene.js`, then reload the panel. No npm install, CDN, external textures or model download is required at runtime. The included verified Windows build tool is esbuild 0.28.2; Three.js is pinned to 0.186.1. Official registry metadata and integrity are retained in the provenance JSON files. MIT notices are in `THREE.LICENSE.txt` and `ESBUILD.LICENSE.txt`.

`height-reference.js` paints the shared bright near-aircraft AGL/launch label in both display backends. `runway.js` builds one two-triangle runway deck whose locally generated mipmapped texture contains all grass, mowing, edge and threshold cues. There are no stacked runway/marking meshes. A stable negative polygon offset keeps that deck over the terrain/grid; the camera uses a 2 m near / 18 km far range instead of the earlier 0.5 m / 30 km range. Ground-trail annotations do not compete for deck depth. This removes the former near-coplanar depth competition; mip filtering also limits high-frequency texture crawl. Chase/Detail framing pulls back about 15 percent for more surroundings. The same framing helper shifts the optical center up 45 px to reserve the bottom 90 px for telemetry, including short 500 x 375 scenes. The shell and connection controls are maintained separately in the parent-owned HTML. Diagnostic elements are optional: frame measurements remain non-visible when the performance element is absent, and optional renderer labels are guarded.

From this directory, run `node verify-motion.mjs` for angle and initial-position guards, and `node verify-display-state.mjs` for the actual display-state regression. The latter validates the included DataFlash BIN hashes, replays 329 actual poses from two flights, rejects late old-session data, checks mode/reposition continuity and exercises the canvas fallback. A separate controlled-arrival test uses 30 actual recorded poses at about 200 ms intervals with 16.7 ms rendering, verifying intermediate motion, normalized quaternion continuity, a monotonic playhead and buffer reset. Results are saved in `fixtures/display-state-result.json`. `node verify-scene-geometry.mjs` builds the actual runway and airframe, checks the single-surface/mipmap/depth-offset contract and fits the whole airframe/canopy across 144 recorded-pose airframe cases and 40 canopy cases in 500/600 px scenes, including 500 x 375 and 584 x 376, above the bottom telemetry overlay. Its saved result is `fixtures/scene-geometry-result.json`. `node verify-height-reference.mjs` verifies the shared height label against an actual recorded AGL sample, four scene sizes, ground/launch datum text, invalid telemetry and the 90 px bottom overlay reserve; its saved result is `fixtures/height-reference-result.json`.

To regenerate the fixture, run `python graphics-source/export-recorded-fixture.py` from the package root with its pymavlink environment. It reads included `runs/first-dive-no-pilot/` and `runs/graphics-restart-reference/`, preserving the original session IDs. No flight process or controls are used.

`benchmark/` contains the archived renderer, its frame meter and the isolated read-only comparison server. Running `python graphics-source/benchmark/server.py` serves `/before` and `/after` on loopback port 8890; it accepts no flight commands. Both views use one recorded actual SITL frame and matching camera parameters. `graphics-performance-results.json` and the before/after PNGs document the historical black-delta revision comparison. Both reached approximately 60 Hz; the improvement is reduced rendering work, not a claimed FPS increase. The normal user panel remains on port 8765.

The previous appearance was the charcoal MQ-9-inspired UAV; `graphics-mq9-live-panel.png` is historical proof of that revision. The saved controlled performance comparison predates this appearance; running the helper again would compare its archived renderer to the current bundle rather than recreate the old black-delta measurement.

`graphics-workstation-live.png` and `graphics-mq9-*` show the previous MQ-9 workstation; black-delta images are older still. See GRAPHICS_TEST_REPORT.md for observed current display counters and responsive checks.

The Orion-inspired silhouette uses broad visual cues only. A first-hand static-display photograph was inspected as a reference: [Boevaya mashina, Orion-E front-right, 2022](https://commons.wikimedia.org/wiki/File:Kronstadt_Orion-E_front_right_ARMY-2022.jpg). No photograph pixels, model, weapons, payloads, real dimensions or aircraft performance data are included. The manufacturer's indexed brochure could not be retrieved (HTTP 502); no claim of an exact technical reproduction is made.

`graphics-orion-compact-live.png` / `graphics-orion-narrow.png` show actual compact-shell flight/descent before the final optical-center adjustment; the shorter final framing is tested by the actual geometry helper. Product diagnostics are optional and can be omitted entirely.
